An AI agent reads your files. That is its job, and no rule stops it. So secretveil does not guard the read. It takes the value out of the file first.

the whole idea, in one file

Before and after

This is your .env file. Nothing else in your project changes.

# before API_KEY=sk-live-Q9xR2mVn7pLwT4aZ DATABASE_URL=postgres://app:s3cr3t-p4ssw0rd-x9@db.internal:5432/app NODE_ENV=development # after API_KEY=sv://api_key # sv: 24 chars, base64, entropy 4.5 DATABASE_URL=postgres://app:sv://database_url_password@db.internal:5432/app NODE_ENV=development

Read the third line. NODE_ENV did not move, because it is not a secret. Read the second line. The host, the user and the database name stayed in the clear. Only the password left. An agent can still write and debug code against that connection. One that saw only sv://database_url could not.

The comment is deliberate. It tells the agent the length, the character set and the entropy. That is enough to write correct code against the variable, and it is not the value. It is also not nothing, so do not put a four digit PIN in the store and expect the comment to hide it.

Almost every other tool picks the left one. The right one is the reason secretveil needs no plugin for your editor, your agent, or the agent that ships next year.

after you run init

Where the value actually lives

Three places, and each one holds a different thing.

.env

safe to read

Handles and shapes. Committed or not, as before. Anyone and anything may read it.

.secretveil/

encrypted

One file, secrets.age, in the age format. init adds this directory to your .gitignore, and doctor checks it is still there.

OS keyring

74 characters

One age identity, and never a secret value. That key opens the file above.

Why the keyring holds a key and not the secrets. On macOS the keychain cuts a value at 128 bytes with no warning, and the other write path puts the plaintext in the process list where every user on the machine can read it. One short key avoids both, and it is what makes a multi line value such as a PEM private key work at all.

a real sequence

What happens when you run

You put four words in front of your command. This is what they do.

$ secretveil run -- npm run dev
01

It reads your .env file and finds every handle in it.

02

It takes the age identity out of your keyring, opens the encrypted store, and reads the real value behind each handle.

03

It puts those values in the environment of the child process, then starts your command.

child env: API_KEY=sk-live-Q9xR2mVn7pLwT4aZ

Your code does not change. dotenv, Vite and Next.js all give a variable in the environment priority over the same name in a .env file. So process.env.API_KEY holds the real value, exactly as it did before.

04

It reads everything that program prints, and puts the handles back before the text reaches your screen, your log, or your agent.

what the program printed Error: connect failed with key sk-live-Q9xR2mVn7pLwT4aZ what you see Error: connect failed with key sv://api_key

The filter works across chunk boundaries, so a value split over two writes is still caught. It matches the encoded forms of each value as well as the value itself. The forms are base64 in both alphabets, hex, the URL escape and the JSON string escape.

the one exception

.npmrc cannot hold a handle

Your .env is read by a framework that respects the environment. Your .npmrc is read by npm itself, straight from disk. A handle in that file would be sent to the registry as if it were the token.

A handle here

breaks npm
.npmrc: sv://npm_token
↓
npm reads the file itself
the registry gets "sv://npm_token"

No framework sits in the middle to swap it back. The login simply fails.

A variable here

works
.npmrc: ${SV_NPMRC_...}
↓
npm expands it from the environment
the registry gets the real token

npm does this expansion on its own. secretveil only has to set the variable.

# before //registry.npmjs.org/:_authToken=npm_A9fK2xQw7ZtR4mVn8sLp3JhG1dYc5B # after //registry.npmjs.org/:_authToken=${SV_NPMRC_REGISTRY_NPMJS_ORG_AUTHTOKEN}

Without secretveil run the variable is unset. npm then sends the literal text ${SV_NPMRC_...} and the registry refuses it. That is the right failure: loud, and with nothing leaked.

who is asking

Three callers, three levels of power

Some commands print a plaintext value. Those need a person.

CallerHow it is recognisedWhat it may do
HumanStandard input and standard output are both a terminalEverything
CIA pipeline marker such as GITHUB_ACTIONS is setEverything. The output filter still runs
AgentA marker such as CLAUDECODE is set, or nothing matchedNo shell, no inline code, no reveal, no restore
An unknown caller is treated as an agent. A command with no terminal and no marker could be a script you wrote, or a tool nobody has heard of yet. The safe reading of an unknown caller is the one with the least power. Set SECRETVEIL_CALLER=human when that is wrong.

Where the line is

A security tool that hides its limits is worse than no tool, because you plan around a protection that is not there.

Stopped

  • The passive read. An agent opens .env and gets a handle.
  • A value that reaches standard output or standard error of your build.
  • The cheap dump: bash -c printenv and its relatives, refused for an agent.
  • A value printed on request. get --reveal and restore both need a person.
the boundary

Not stopped

  • A program that receives a value can write it anywhere. It has to receive it, or it cannot connect to your database.
  • The command rules read a name, not a program. npm run build is allowed, and that script can hold printenv.
  • A secret that already leaked. Rotate first, install second.
  • A very short value. The filter will not remove a four character run from your output.

The honest summary: secretveil removes the accidental leak, which is the common one. Your agent reads .env because reading files is what it does all day. It does not stop a deliberate attack by something that already runs your build scripts.

The whole workflow

secretveil plan # see what would change. Writes nothing. secretveil init # move the values out, put handles in secretveil doctor # check the setup, name what it cannot protect secretveil run -- npm run dev secretveil run -- npm install secretveil restore # undo it. Byte for byte. Needs a person.
